# 冷启动分批读取与缓存复用

## 问题与依据

- 用户反馈每次进入都需要等待相册分析，要求更快或流式、后台线程读取。
- 0.3.3 已有后台元数据读取、独立分析 actor 和增量变更通知，但冷启动仍逐张枚举全库资源后才发布列表；未分析照片的普通元数据没有完整保存。
- 列表统计与分类计数在主线程生成；这次没有真机阶段耗时，不能把以上源码成本等同于用户全部等待时间。

## 实现

1. PhotoKit 在后台先读取 128 项，随后每批最多 1,024 项。等待消费者完成列表发布和必要保存后再读取下一批，不积压无界队列。
2. 按当前权限与照片 ID 核对缓存；照片版本、尺寸和媒体属性不变时复用文件名、资源类型及分析结果，不重复枚举资源。变化与缺失版本信息仍走完整核对。
3. 保存新增和变化的元数据，包括尚未分析的照片；旧版 JSON 分片和特征文件格式保持兼容。
4. 将快照统计移到后台。首批加载后允许浏览和暂存整理动作；正式删除、收藏提交、标签保存仍等待读取完成。
5. 保留已有 PhotoKit 增量通知、断点分析和系统删除确认；冷启动仍做轻量权限与版本核对，不直接展示未经当前授权核对的磁盘缓存。

## 边界

- 后台线程读取不会保证 App 切到桌面后持续运行；iOS 决定后台执行与挂起，仍按已有机制保存进度。
- 冷启动仍需读取本机 JSON 索引并核对当前图库；不承诺零读取或固定秒数。
- 几万项图库首屏时间、总耗时、峰值内存，以及用户目标手机上的实际体验仍需真机验收。
